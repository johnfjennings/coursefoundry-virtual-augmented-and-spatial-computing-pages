Practical

Interaction Technique Bake-Off

Author

Mr. John Jennings

Overview

Duration: 2 hours (plus 30–45 minutes of project setup before the session) Software: Unity 6.3 LTS, XR Interaction Toolkit 3.x, XR Hands, OpenXR Hardware: Meta Quest 3 / 3S with controllers and hand tracking enabled, or a Windows or Apple Silicon Mac computer running the Meta XR Simulator (see the no-headset alternative)

The lecture introduced ray casting, direct manipulation and gaze-plus-pinch as alternatives with different costs. This practical stops the argument being theoretical: you implement the same task three ways and measure which is actually faster, more accurate and less tiring.

Objectives

By the end of this practical, you will be able to:

  • Configure a Unity 6 project for Meta Quest using OpenXR and the XR Interaction Toolkit 3.x
  • Implement one identical task using three distinct input modalities
  • Design and run a fair timed comparison across the group
  • Quantify a modality trade-off rather than asserting it

Prerequisites

  • Unity 6.3 LTS installed through Unity Hub with Android Build Support (including OpenJDK and Android SDK & NDK Tools)
  • A Quest headset in developer mode, with hand tracking switched on in the headset’s settings
  • The trial recording sheet supplied on the VLE
NoteNo Quest headset?

You can complete this practical on a Windows or Apple Silicon Mac computer using the Meta XR Simulator in place of the headset. Follow the normal project setup, then the changes in Alternative: Working Without a Headset. Each part of the practical tells you what differs.

WarningMost online tutorials are for XRI 2.x

The XR Interaction Toolkit changed significantly in version 3.0. If a tutorial tells you to add an XR Controller (Action-based) component, or to drag in an XR Interaction Setup prefab, it is written for 2.x and those steps no longer apply. In 3.x:

  • Input is configured directly on each interactor (Select Input, Activate Input).
  • The rig prefab is XR Origin (XR Rig), or XR Origin Hands (XR Rig) for hand tracking.
  • Scripts need new namespaces, for example UnityEngine.XR.Interaction.Toolkit.Interactables and UnityEngine.XR.Interaction.Toolkit.Interactors.

The XRI 3.0 upgrade guide lists every change.

Before the Session: Project Setup (30–45 minutes)

Do this at home or in a free lab slot. Installing packages and building to Android the first time is slow, and it should not eat into the timed parts of the practical.

  1. Create the Project
    • In Unity Hub, create a new project using the Universal 3D (URP) template in Unity 6.3 LTS.
    • Open File > Build Profiles, select Meta Quest and click Switch Platform.
  2. Enable OpenXR for Quest
    • Open Edit > Project Settings > XR Plug-in Management and install it if prompted.
    • On the Android tab, tick OpenXR and the Meta Quest feature group.
    • Under XR Plug-in Management > OpenXR (Android tab), enable the features Meta Quest Support, Hand Tracking Subsystem and Meta Hand Tracking Aim.
    • Under Enabled Interaction Profiles, add Oculus Touch Controller Profile and Hand Interaction Profile.
    • Open Project Validation (the warning icon on the same page) and click Fix All until nothing is left.
  3. Install the Interaction Packages
    • In Window > Package Manager > Unity Registry, install XR Interaction Toolkit (3.3.2 is the version verified for Unity 6.3; any later 3.x also works) and XR Hands.
    • On the XR Interaction Toolkit’s Samples tab, import Starter Assets and then Hands Interaction Demo. Accept the prompt to install Shader Graph if it appears.
  4. Smoke Test
    • Open the Hands Interaction Demo scene from the imported samples, then Build And Run it to the headset.
    • Pick up an object with a controller, put the controllers down, and pinch an object with your hand. If both work, the project is ready.

Alternative: Working Without a Headset

The Meta XR Simulator is a desktop OpenXR runtime that presents a simulated Quest 3 to your application. Unity talks to it exactly as it would talk to a real headset, so your scenes, rig and scripts stay the same. The difference is that you drive the head, controllers and hands with a keyboard and mouse or an Xbox controller, and everything runs in Play mode on your computer instead of as an Android build.

Simulator Setup (in place of the Smoke Test)

Complete steps 1 to 3 of the project setup above first. You still need the Android/Meta Quest configuration if you want to hand your project to someone with a headset later.

  1. Check Your Computer
    • Windows 10 or later (64-bit), or macOS on Apple Silicon. Intel Macs are not supported.
    • The simulator supports Vulkan, Direct3D 11 or 12 on Windows, and Vulkan or Metal on macOS. It does not support OpenGL. Unity’s defaults already meet this.
  2. Install the Simulator
    • Download and install the standalone app: Windows or macOS (Apple Silicon).
    • The old Meta XR Simulator package on the Unity Asset Store is deprecated. Do not install it. A project that uses OpenXR needs no extra Unity package.
  3. Enable OpenXR for the Desktop
    • In Edit > Project Settings > XR Plug-in Management, open the Windows, Mac, Linux tab (the monitor icon) and tick OpenXR.
    • Under OpenXR on the same tab, add Oculus Touch Controller Profile and Hand Interaction Profile, and enable Hand Tracking Subsystem (and Meta Hand Tracking Aim if it is listed).
    • Run Project Validation for this tab and fix all issues.
    • In Edit > Project Settings > XR Interaction Toolkit, untick Use XR Interaction Simulator in scenes if it is ticked. Otherwise Unity’s own simulator and Meta’s simulator will both try to drive the rig.
  4. Make the Simulator the Active OpenXR Runtime
    • Open the Meta XR Simulator app and switch on the toggle in its top-left corner. This makes it your computer’s active OpenXR runtime.
    • Only one OpenXR runtime can be active at a time. While the simulator is on, Meta Horizon Link will not work. Switch the toggle off when you finish, and your previous runtime is restored.
    • Full instructions: Get Started with Meta XR Simulator and activating the simulator for OpenXR-only projects.
  5. Smoke Test in Play Mode
    • Open the Hands Interaction Demo scene and press Play. The simulator window shows the view from the simulated headset, with a Quest 3 as the default device.
    • Move with W A S D, and hold the right mouse button and move the mouse to look around.
    • Open the simulator’s Input bindings panel. Note which keys press the grip and trigger, how you switch the active input between controller and hand, and which key makes the hand pinch. Write these on your recording sheet, because you will use them in every trial.
    • Pick up an object with a simulated controller, then switch the input to hands and pinch an object. If both work, you are ready.
    • Between runs, leave the simulator open and just exit Play mode. The next launch is much faster.
TipBetter input devices

Keyboard and mouse control is awkward for 3D manipulation. If you have an Xbox controller, select it as the Left and Right input source in the simulator’s Inputs panel. It gives analogue sticks and triggers that map much more naturally onto Quest controllers. See keyboard, mouse and Xbox controller mappings.

What Changes in Each Part

  • 1.1 Shared scene: no changes. Build it exactly as described.
  • 1.2 Variant A (ray + trigger): no changes to the scene. In the simulator, aim the controller ray with the mouse and use the bound trigger key to select.
  • 1.3 Variant B (direct grab): no changes to the scene. With the participant standing still, the simulated hand must be moved forward to reach the cubes. The effort of reaching becomes a keyboard task, not a physical one. Record this as a limitation.
  • 1.4 Variant C (head-gaze + pinch): set up as described. In the simulator the “head” is the mouse look, so head-gaze becomes mouse-pointing and the pinch is a key press. If simulated hands do not appear, switch the input source to hands in the Inputs panel. If they still do not appear, use the Gaze Assistance fallback with a controller ray.
  • 1.5 Feedback: haptics cannot be felt in the simulator. Turn haptics off in all variants so every participant experiences the same feedback.
  • Testing: press Play instead of Build And Run. There is no Android build, and there is no need for adb to collect data.

What Changes in the Trials and Analysis

  • Data location: trials.csv is written to your computer at Application.persistentDataPath:
    • Windows: %USERPROFILE%\AppData\LocalLow\<Company Name>\<Product Name>\
    • macOS: ~/Library/Application Support/<Company Name>/<Product Name>/
    Add Debug.Log(Application.persistentDataPath); to Start() if you cannot find it.
  • Label your data: give simulator participants IDs such as S01. Simulator trials are not comparable with headset trials, because you are measuring mouse and keyboard skill, not arm movement. Keep them as a separate group when pooling the class results.
  • Subjective measures: still record the one-to-seven effort rating, but interpret it as control effort. Arm and neck fatigue will not appear. Note wrist or hand strain instead.
  • Analysis: answer the Part 3 questions for your simulator data. Then add one paragraph comparing your ranking of the three modalities with the headset group’s ranking. Where do they disagree, and what does the simulator hide about each modality? Think especially about the gorilla-arm effect and about Fitts’ Law, which the simulator turns into mouse travel.

Instructions

Part 1: Build the Three Variants (55 minutes)

1.1 The Shared Task Scene (15 minutes)

The task is fixed for everyone: select the highlighted cube from nine cubes arranged on an arc and place it into a target socket. Every group uses the same dimensions so results can be pooled.

  1. Save a Scene Copy
    • Create a new scene called BakeOff_Base. Add a floor plane and a small marker at the origin showing where the participant stands.
    • Do not add a rig yet. Each variant scene adds its own.
  2. Place the Cubes
    • Create a cube, scale it to 0.06 and name it Cube_1. Add an XR Grab Interactable component, which also adds a Rigidbody.
    • On the Rigidbody, untick Use Gravity and tick Is Kinematic, so the cubes hang in place.
    • On the XR Grab Interactable, untick Throw On Detach.
    • Duplicate the cube until you have nine, positioned on the arc as follows (y = 1.0 for all; rotate each cube by the given Y angle so it faces the user):
    Cube Angle (Y rotation) x (m) z (m)
    1 −60° −0.520 0.300
    2 −45° −0.424 0.424
    3 −30° −0.300 0.520
    4 −15° −0.155 0.580
    5 0° 0.000 0.600
    6 15° 0.155 0.580
    7 30° 0.300 0.520
    8 45° 0.424 0.424
    9 60° 0.520 0.300
  3. Build the Socket
    • Add a cylinder pedestal whose top sits at 0.9 m, positioned at x = 0, z = 0.4.
    • Create an empty GameObject Socket just above the pedestal. Add an XR Socket Interactor and a Sphere Collider (tick Is Trigger, radius 0.06).
    • Create a child empty called Attach and assign it to the socket’s Attach Transform. This is the pose the cube snaps to.
    • Leave Show Interactable Hover Meshes on. It draws a ghost of the cube when one hovers over the socket, which gives the “hover” state from the lecture for free.
  4. Add the Trial Manager
    • Create two materials, Target (orange) and Distractor (pale blue).
    • Create an empty GameObject TrialManager and add the script below. Assign the socket, the nine cubes in arc order and the two materials.
TrialManager.cs
using System.Collections;
using System.Collections.Generic;
using System.IO;
using UnityEngine;
using UnityEngine.XR.Interaction.Toolkit;
using UnityEngine.XR.Interaction.Toolkit.Interactables;
using UnityEngine.XR.Interaction.Toolkit.Interactors;

public class TrialManager : MonoBehaviour
{
    [SerializeField] XRSocketInteractor socket;
    [SerializeField] List<XRGrabInteractable> cubes;   // Cube_1 .. Cube_9, in arc order
    [SerializeField] Material targetMaterial;
    [SerializeField] Material distractorMaterial;
    [SerializeField] string participant = "P01";
    [SerializeField] string variant = "A";
    [SerializeField] int trialsPerBlock = 10;

    readonly List<Pose> homePoses = new();
    int trial;
    int target;
    float startTime;

    void Awake()
    {
        foreach (var cube in cubes)
            homePoses.Add(new Pose(cube.transform.position, cube.transform.rotation));
    }

    void OnEnable() => socket.selectEntered.AddListener(OnPlaced);
    void OnDisable() => socket.selectEntered.RemoveListener(OnPlaced);
    void Start() => NextTrial();

    void NextTrial()
    {
        target = Random.Range(0, cubes.Count);
        for (int i = 0; i < cubes.Count; i++)
            cubes[i].GetComponent<Renderer>().sharedMaterial = i == target ? targetMaterial : distractorMaterial;
        startTime = Time.time;
    }

    void OnPlaced(SelectEnterEventArgs args)
    {
        var placed = args.interactableObject as XRGrabInteractable;
        int placedIndex = cubes.IndexOf(placed);
        float seconds = Time.time - startTime;
        int error = placedIndex == target ? 0 : 1;

        // Written to the headset: Android/data/<your.package>/files/trials.csv
        File.AppendAllText(Path.Combine(Application.persistentDataPath, "trials.csv"),
            $"{participant},{variant},{trial + 1},{target + 1},{placedIndex + 1},{seconds:F3},{error}\n");

        StartCoroutine(ResetCube(placed, placedIndex));
    }

    IEnumerator ResetCube(XRGrabInteractable cube, int index)
    {
        yield return null;  // let the socket finish its select before we release it
        socket.interactionManager.SelectExit(socket, (IXRSelectInteractable)cube);
        cube.transform.SetPositionAndRotation(homePoses[index].position, homePoses[index].rotation);

        trial++;
        if (trial < trialsPerBlock)
            NextTrial();
        else
            Debug.Log($"Block {variant} complete for {participant}");
    }
}
  • Placing the wrong cube is logged as an error. Dropping a cube outside the socket is not logged automatically: the observer should tally drops on the recording sheet.
  1. Save Three Copies
    • Save BakeOff_Base three times as BakeOff_A_Ray, BakeOff_B_Direct and BakeOff_C_GazePinch. Change only the rig and the variant field in each. Lighting, scale, cube layout, materials and audio must stay identical.

1.2 Variant A: Ray Interactor with Trigger Select (12 minutes)

The user points from a distance and pulls the trigger to pick up.

  1. Open BakeOff_A_Ray. From Samples/XR Interaction Toolkit/<version>/Starter Assets/Prefabs, drag XR Origin (XR Rig) onto the standing mark.
  2. Disable locomotion so the participant cannot walk to the cubes: turn off the Locomotion child object and each controller’s Teleport Interactor.
  3. On each controller, disable the Poke Interactor.
  4. Select each controller’s Near-Far Interactor:
    • Untick Enable Near Casting and keep Enable Far Casting ticked, so it behaves as a pure ray.
    • Under Input Configuration, change Select Input to that hand’s Activate action (the trigger) instead of the default grip action. This matches the lecture’s “ray + trigger” technique.
  5. Build and check: the ray should highlight a cube, the trigger should pick it up, and releasing the trigger over the socket should snap it in.
NoteTutorials and documentation: ray interaction
  • Unity Learn, Create with VR 2.3: Near-Far and Ray Interactors
  • XRI docs: Near-Far Interactor and XR Ray Interactor
  • Official XRI Examples project: Grab Interactables station (ray and direct grab side by side)

1.3 Variant B: Direct Interactor (12 minutes)

The user must physically reach the cube and squeeze the grip.

  1. Open BakeOff_B_Direct and add the same XR Origin (XR Rig), with locomotion, teleport and poke disabled exactly as in Variant A.
  2. On each controller’s Near-Far Interactor, tick Enable Near Casting and untick Enable Far Casting. Leave Select Input on the default grip action.
    • Alternative: disable the Near-Far Interactor and add an XR Direct Interactor with a small trigger Sphere Collider at the controller tip.
  3. Build and check that a cube can only be picked up when the controller physically overlaps it. At 0.6 m, most participants reach the end cubes (1 and 9) by leaning or stepping. Note on the sheet whether they did.
NoteTutorials and documentation: direct interaction
  • Unity Learn, Create with VR 1.3: Grabbable GameObjects (direct grab section)
  • XRI docs: XR Direct Interactor and Near-Far Interactor (near casting)
  • Video: Valem Tutorials, How To Make a VR Game in 2 Hours: Complete Beginner Tutorial Unity 6 (2026; covers setup and grabbing)

1.4 Variant C: Gaze (Head Pointing) plus Pinch (16 minutes)

The user looks at the cube and pinches to confirm. No controllers are held.

ImportantThe Quest 3 has no eye tracking

Only the Quest Pro has eye trackers. On the Quest 3 and 3S, the XR Gaze Interactor falls back to head pose: the “gaze” ray comes from the centre of the headset. Record this as head-gaze in your write-up, and think about how true eye tracking might change your results.

  1. Open BakeOff_C_GazePinch. From the Hands Interaction Demo sample, drag XR Origin Hands (XR Rig) onto the standing mark. Disable locomotion and teleport as before.
  2. Find the Gaze Interactor under the rig’s Camera Offset and enable it. On the Gaze Input Manager component, tick Fallback If Eye Tracking Unavailable. Without this, the gaze interactor switches itself off on a Quest 3.
  3. On the XR Gaze Interactor:
    • Untick Hover To Select. We want gaze plus confirm, not dwell selection, which is the Midas Touch problem from the lecture.
    • Under Input Configuration, set Select Input to the right hand’s Select action from XRI Default Input Actions. With hands, this action is bound to the pinch.
  4. On every cube’s XR Grab Interactable, tick Allow Gaze Interaction and Allow Gaze Select.
  5. Disable the hands’ own ray and near interactors so the pinch only confirms the gaze target and cannot grab anything by itself.
  6. Build and test early. Look at a cube, pinch, turn your head towards the socket and release the pinch over it. If the cube jumps towards your face on selection, set the cube’s Far Attach Mode to Far, so it stays at the distance where it was selected.
TipFallback if Variant C will not cooperate

XRI’s Gaze Assistance gives a closely related technique. Keep the hand’s ray interactor enabled and tick Allow Gaze Assistance on each cube. The hand ray then snaps to whichever cube you look at, and the pinch confirms. Whichever version you build, record it in your write-up so the class knows which technique was measured.

1.5 Keep the Feedback Identical

The lecture’s feedback triad applies here. Feedback must not differ between variants, or you will measure the feedback rather than the modality.

  • Add a short click AudioSource to the socket and play it from the socket’s Select Entered event, in all three scenes.
  • Controllers can vibrate but hands cannot. Either turn haptics off in Variants A and B, or leave them on and record this as a known difference between the conditions. Agree on one choice as a class before anyone runs trials.
NoteDocumentation: feedback
  • Unity Learn, Create with VR 2.1: Audio and Haptics
  • XRI docs: Simple Haptic Feedback. The older affordance system is deprecated in XRI 3.
TipTest in the Editor first

The XR Interaction Simulator lets you drive the rig with mouse and keyboard in Play mode, including simulated hands. Check that each variant works before you spend time on an Android build.

Part 2: Run the Trials (35 minutes)

  1. Protocol
    • Each participant completes ten placements per modality: one block of ten per scene.
    • Randomise the order of modalities per participant to control for practice effects. With three variants there are six possible orders (ABC, ACB, BAC, BCA, CAB, CBA), so assign one order to each participant in turn.
    • Before each block, set the participant and variant fields on the TrialManager.
    • Allow three untimed practice placements per modality before the block starts.
    • The participant stands on the marker and does not step off it. The observer tallies dropped cubes and any stepping or leaning on the sheet.
  2. Collect the Data
    • trials.csv is written to the headset. Copy it off with Meta Quest Developer Hub (File Manager) or with adb pull /sdcard/Android/data/<your.package.name>/files/trials.csv.
    • The columns are: participant, variant, trial, target cube, placed cube, time in seconds, error (1 = wrong cube).
    • Using the simulator? The file is on your computer instead. See What Changes in the Trials and Analysis.
  3. Subjective Measures
    • After each modality, record a one-to-seven rating for perceived effort.
    • Note any comment about arm or neck fatigue, and at which trial number it first appeared. Head-gaze tends to move the fatigue from the arm to the neck.

Part 3: Analysis (30 minutes)

  1. Pool and Compare
    • Pool the class CSV files and compare mean completion time and error rate across modalities.
    • Relate the pattern to Fitts’ Law. The movement distance D is from the target cube to the socket, so the end cubes (1 and 9) are the long-distance targets and cube 5 is the shortest. Did completion time rise with distance equally for all three modalities?
  2. Draw a Conclusion
    • State which modality you would choose for a task performed once, and for a task repeated for twenty minutes.
    • These are frequently different answers. Explain why.
    • Note how your Variant C result might change on a headset with true eye tracking.

Expected Outcome

Three working variants of the same task, a completed trial dataset across the group, and a short written comparison of completion time, error rate and perceived effort with a justified recommendation for two different usage patterns.

TipHint

Randomise the order for every participant. If everyone tries ray casting first, you will have measured how quickly people learn the task rather than how good the modality is.
